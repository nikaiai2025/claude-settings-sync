# spec-scaffold

実装に入る前に「全体の枠組み」をビジネスオーナーとの契約として文書化し、以後の設計・実装をここから逸脱させないためのスキル。specは「何を」、decisions（ADR）は「なぜ」を持つ——この分離を崩さない。

## 成果物

リポジトリ直下に以下を作成する（既存があれば更新）：

- `spec/product.md` — プロダクト契約（下記構造）
- `spec/architecture.md` — 基本設計（アーキテクチャレベルのみ。規約・データ出所などの運用制約もここ）
- `spec/design-notes.md` — 詳細設計の台帳（検討・確認事項の記録）
- `spec/decisions.md` — 判断と棄却案の記録（ADR相当。無ければ作る）
- `spec/DESIGN.md` — デザインポリシー（画面実装への移行時に作成。方向・原則・デザイントークン・写真/操作感の基準・範囲外を20〜30行で）。画面の受け入れ基準として確認時に一致を検証し、トークン値の正はここに置いて実装（テーマ・デザインツール変数）へ反映する

調査・ブレスト等の過程物は `docs/` に置く（静的アーカイブ。結論だけ使い、再調査しない。役目を終えたら削除可）。

作成後、リポジトリの `CLAUDE.md` の必読節に spec/ を追記し（「実装・設計はここから逸脱しない」）、`プロジェクト状況.md` を更新する。

## product.md の構造

1. **コアコンセプト**：3〜5行の自然文。このシステムが誰に何を提供するかを端的に。差別化軸を1つ明記
2. **スコープ外**：やらないこと3〜5点。棄却理由は書かない（decisionsへのリンクのみ）
3. **コア体験**：3〜5個。「〇〇のユーザーが、××を通じて、△△を達成（気持ち：□□）」の形式。コンセプトの分解であること。段階リリースなら［〜段階］を付す
4. **成功指標**：体験ごとに観測可能な指標を1〜2個（例：完了率、タップ数、ゼロ件率）
5. **システムの振る舞い**：体験ごとに3個程度のシナリオ。自然文だが「前提→操作→結果」の順を保つ（厳密なGherkin記法は不要）。横断的なものは「共通の振る舞い」に
6. **主要な画面**：表形式で「画面／達成すること／接続先」。ボタンレベルのオブジェクト定義・ワイヤーフレームは書かない

## architecture.md の構造

展開形態（プラットフォーム・機能分割）／インフラ構成（サービス名と役割分担）／外部依存とコスト制御（無料枠・課金トリガー）／データ（保存対象・規約制約・単一情報源）。関連する非機能要件（コスト上限・プライバシー・性能）は該当するものだけを該当節に書く。

## design-notes.md の構造

実装前に検討・確認が必要な事項の台帳。項目ごとに「意義（1〜2行）／確定事項（根拠へのリンク）／**未決**（論点の列挙）」。結論が出たら確定に移し、1項目が肥大したら独立文書に分離して台帳にはリンクを残す。

## テスト戦略の標準形（実装移行時に design-notes へ立てる）

実装着手時に「実装・テスト戦略」項目を design-notes に立て、以下を既定形とする（逸脱するなら理由を明記）：

- **層構成（結合厚め）**：①契約・変換の golden（決定的なマスタ・変換表のスナップショット）②結合テスト（本番同等ランタイムで実行。外部APIは fetch 境界の合成フィクスチャ——規約上レスポンス保存不可なら録画リプレイも禁止）③E2E はスタブ既定、実APIは最小スモークに分離（課金・規約対策）④ラップ型アプリは WebView を Web E2E で賄い、ネイティブ殻の差分のみ smoke（Maestro 等）
- **シナリオ管理**：日本語 Gherkin＋playwright-bdd を「実行可能な仕様」としてリポジトリ管理。外部テスト管理ツールは使わない（DRY）
- **Gherkin 増殖制御**：feature はコア体験＋横断系に対応する固定構成（10未満・新規はオーナー判断）／昇格は「ユーザーに約束する振る舞い」のみで網羅はコード層に置く／宣言的記法・同型は Examples で畳む／ステップ辞書を共有し同義ステップを新設しない／総量20〜30本目安、超過は統廃合（アーカイブせず削除。履歴はgit）
- **決定性**：乱数はシード注入可能に設計、モード分岐はフラグ強制で両側をテスト
- **エージェント型ブラウザ操作**：開発時の動作確認・探索専用（探索→コードへ固定化）。CI 回帰はコード化テストを正とする（規準：無人・決定的・毎コミット）
- **ネイティブ側の開発時診断**：ADB を同位置づけで使う（実機フレーム計測・WebView 接続・権限付け外し・ディープリンク起動・logcat）。エージェントに端末操作させる場合は mobile-mcp 等の MCP を検討。CI 回帰はネイティブ殻 smoke（Maestro 等）を正とする

## 品質規則

- **トレーサビリティ**：コンセプト1→体験3〜5→体験1あたりシナリオ3程度→画面は振る舞いに対応。どこにも紐づかない記載はスコープクリープとして削除する
- **剃刀**：システムの動作を変えない記述は書かない
- **未決の明示**：決まっていないことを決まったかのように書かない。未決は design-notes に集約し、specの本文には確定事項だけを書く
- **契約の変更は明示的に**：specを黙って書き換えない。既存決定と矛盾する変更は矛盾を指摘した上で、改訂として decisions に記録する
- **用語**：独自用語は製品の核心でオリジナリティが高い概念だけに定義する（用語集は数語まで）。それ以外は一般的な言葉を使い、内輪の略語・比喩を文書に持ち込まない
- **分量**：各文書100行程度まで。根拠・調査結果は docs/ に置きリンクで参照（DRY）

## 作成手順

1. ヒアリング：コンセプト／対象ユーザーと利用状況のバリエーション／やらないこと。不明点は仮置きせず質問する
2. product.md を草案→ユーザー確認（コンセプトと体験の文言が本人の言葉として違和感ないかを必ず確認する）
3. architecture.md・design-notes.md を作成（技術的な想定は「想定」と明記し、確定と区別する）
4. CLAUDE.md 必読への追記とプロジェクト状況.md 更新

## アンチパターン

- ワイヤーフレームや網羅的SRSを書き始める（このスキルの範囲外）
- 判断の根拠・棄却案を product / architecture に書き込む（decisions へ）。逆に、現行設計の「何を」を decisions に重複記載する
- 未決を埋めるために仮決めを断定形で書く
- 体験に紐づかない機能を振る舞い・画面に足す
- 調査結果の本文をspecに複製する（リンクで参照）
